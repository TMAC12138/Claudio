# Claudio 待播队列刷新与喜欢歌曲设计

## 背景与目标

播放器当前通过 `GET /api/next` 获取 11 首推荐：第一首立即播放，其余歌曲进入待播队列。播放器侧边栏目前只有静态的待播预览，歌曲标题也没有直接维护个人品味的入口。

本次改动包含两个目标：

1. 在 “Up Next” 区域增加刷新按钮。点击后保持当前歌曲、播放状态和播放进度不变，仅用新推荐结果替换待播队列。
2. 在当前歌曲标题旁增加爱心按钮。用户可以把当前歌曲加入 `user/taste.md`，再次点击则删除该喜欢记录。

不在本次范围内：收藏歌单管理、收藏时间或备注、数据库收藏表、历史喜欢记录迁移、改变现有播放和跳过规则。

## 方案选择

采用专用接口方案：为队列刷新和喜欢状态增加边界清晰的服务端接口，不复用会产生播放记录的 `/api/next`，也不让前端读取后覆盖整篇 `taste.md`。

未采用的方案：

- 复用 `/api/next` 与 `/api/taste`：改动较少，但刷新队列会把尚未播放的歌曲记入播放历史，整篇文档覆盖也可能丢失并发修改。
- 新增收藏数据库并同步 Markdown：一致性更强，但超出当前功能需要，增加了双写和迁移复杂度。

## 队列刷新

### 界面

- 在 “Up Next” 标题行加入 `刷新推荐` 按钮。
- 点击后按钮进入加载状态并禁用，避免重复请求。
- 成功后恢复按钮状态，并用新结果替换现有待播队列。
- 失败时保留原队列，恢复按钮，并通过紧邻按钮的 `aria-live` 状态文本提示失败。
- 当前歌曲、音频元素 `src`、播放或暂停状态、播放进度和历史栈均不得改变。
- 待播预览展示新队列的前两首；队列计数显示完整待播数量。

### 数据流

1. 前端调用新的队列刷新 API。
2. 服务端让 Claude 生成推荐，并通过 NCM 解析可播放歌曲。
3. 服务端返回最多 11 首可播放歌曲，但不调用 `db.recordPlay()`。
4. 前端用返回数组整体替换内存中的 `queue`；新数组第一首也属于待播队列，不会立即播放。
5. 当前歌曲自然结束或用户跳过时，继续消费新队列的第一首。

### 接口

`POST /api/queue/refresh`

成功响应沿用推荐结果结构：

```json
{
  "say": "推荐说明",
  "play": [
    {
      "id": "song-id",
      "name": "歌曲名",
      "artist": "歌手",
      "url": "/api/audio/song-id"
    }
  ],
  "reason": "推荐理由"
}
```

接口只生成和解析候选，不写播放历史。Claude 或 NCM 失败时返回非 2xx 错误或空候选错误，前端不得清空原队列。

## 喜欢歌曲

### 文档格式

服务端只维护 `user/taste.md` 中以下受控区块：

```markdown
## 我喜欢的歌曲

- 《多远都要在一起》 — G.E.M.邓紫棋
```

歌曲以规范化后的 `歌曲名 + 歌手` 作为唯一键。新增歌曲时，如果区块不存在，则在文档末尾创建；取消喜欢时只删除完全匹配的受控列表项。区块外的既有自然语言内容保持原样，不进行迁移或改写。

为防止 Markdown 换行破坏格式，服务端写入前将歌曲名和歌手中的换行折叠为空格并去除首尾空白。缺少歌曲名时拒绝请求；歌手缺失时使用 `未知歌手`。

### 界面与状态

- 在 `#song-title` 同一标题行增加爱心按钮。
- 尚未加载歌曲时按钮禁用。
- 切换歌曲后查询该歌曲的喜欢状态：喜欢时显示实心爱心并设置 `aria-pressed="true"`，否则显示空心爱心。
- 点击时按钮进入忙碌状态，服务端成功后再确认最终状态。
- 写入失败时保持操作前状态，并通过 `aria-live` 文本提示失败。
- 连续收藏同一首歌不会重复写入；连续取消同一首歌也不会影响文档其他内容。

### 接口

`GET /api/taste/favorite?name=<歌曲名>&artist=<歌手>`

```json
{
  "liked": true
}
```

`POST /api/taste/favorite`

```json
{
  "name": "多远都要在一起",
  "artist": "G.E.M.邓紫棋",
  "liked": true
}
```

响应返回服务端最终状态：

```json
{
  "ok": true,
  "liked": true
}
```

`liked: false` 表示从受控区块删除该歌曲。

## 代码边界

- `server.js`：注册两个新接口，并调用独立的品味文档辅助模块。
- `lib/taste.js`：负责输入规范化、受控区块解析、幂等添加和精确删除，不包含 HTTP 或 DOM 逻辑。
- `public/js/api.js`：封装队列刷新、喜欢状态查询和喜欢状态写入。
- `public/js/player.js`：管理队列替换、待播预览、爱心状态及忙碌/错误状态。
- `public/js/app.js`：绑定新增按钮事件。
- `public/index.html`、`public/css/style.css`：增加按钮、状态文本和必要样式。

只修改完成上述功能所需的代码，不重构现有播放器或品味编辑器。

## 错误处理与并发

- 队列刷新使用现有 `loadingNext` 之外的独立忙碌状态，避免刷新按钮与播放/跳过按钮互相改变标签。
- 如果刷新进行时当前歌曲结束，播放器仍可消费旧队列；仅在刷新请求成功返回时原子替换剩余队列。
- 爱心按钮在请求期间禁用，防止同一页面重复提交。
- 服务端每次写入都基于磁盘中的最新 `taste.md` 内容，并通过临时文件加重命名的方式完成原子替换，避免半写入文件。
- 页面在喜欢状态请求返回前又切换歌曲时，旧请求结果不得覆盖新歌曲的按钮状态。

## 验收与测试

自动化测试至少覆盖：

- 添加喜欢歌曲时创建受控区块和列表项。
- 重复添加同一 `歌曲名 + 歌手` 不产生重复项。
- 取消喜欢只删除精确匹配项，不改动区块外内容或其他歌曲。
- 歌曲名和歌手包含换行、Markdown 标点或非 ASCII 字符时仍可稳定往返。
- 队列刷新成功后替换完整待播队列，同时当前歌曲对象保持不变。
- 队列刷新失败时保留旧队列。
- 喜欢请求失败或过期响应不会污染当前歌曲的爱心状态。

完成前验证：

1. 运行新增单元测试和现有健康检查。
2. 运行 JavaScript 语法检查。
3. 在 `http://127.0.0.1:3000/` 验证页面身份、控制台健康和无框架错误遮罩。
4. 播放一首歌，点击刷新，确认歌曲与进度不变、队列内容和计数更新。
5. 点击爱心，确认按钮点亮且 `user/taste.md` 出现一条记录；再次点击，确认按钮复原且该记录删除。
6. 在桌面视口和一个移动视口检查标题与按钮无重叠、裁切或不可点击问题。
